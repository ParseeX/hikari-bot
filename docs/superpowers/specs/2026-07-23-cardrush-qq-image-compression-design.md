# Cardrush QQ 图片压缩设计

## 背景

Cardrush 图报由 Playwright 渲染为原始 PNG。QQ 适配层随后把 PNG
编码为 Base64 并通过 OneBot 发送。带有大量卡图时，单页 PNG 可能达到
数 MB，使 NapCat/QQNT 的 `sendMsg` 更容易发生 `retcode=1200`
发送确认超时。

本次以“发送给 QQ 的单页图片不超过 1,000,000 字节”为试行阈值。
该阈值是可调整的工程参数，不视为 QQ 官方限制。

## 目标

- QQ 发送前将每页图报压缩为不超过 1,000,000 字节的 JPEG。
- 手动“卡价图报”和自动 QQ 日报使用相同压缩逻辑。
- B 站发布及其他消费者继续使用 Playwright 生成的原始 PNG。
- 保持图片宽高比，并尽量优先保留分辨率与可读性。
- 记录每页压缩前后的字节数，为后续调整阈值提供依据。

## 非目标

- 不改变 HTML、CSS、卡图下载或 Playwright 页面布局。
- 不实现 `retcode=1200` 自动重试，避免超时后实际送达造成重复图片。
- 不把 1 MB 当作绝对成功保证。
- 不改变 B 站发布占位逻辑。

## 方案

新增一个不依赖 NoneBot 的纯图片压缩模块。压缩只由 QQ 适配层调用，
报表工作流仍返回原始 PNG。

公开接口：

```python
compress_for_qq(
    image_bytes: bytes,
    max_bytes: int = 1_000_000,
) -> bytes
```

处理流程：

1. 用 Pillow 解码输入图片并转换为适合 JPEG 的 RGB 图像。
2. 从 JPEG 质量 85 开始编码。
3. 若超过上限，以 5 为步长降低质量，最低降至 40。
4. 质量 40 仍超限时，将宽高等比缩小至原来的 85%，然后从质量 85
   重新尝试；最小宽度为 640 像素。
5. 达到上限后返回 JPEG 字节。
6. 输入无法解码或在安全下限内仍无法压缩时，抛出
   `CardrushRenderError`，不发送不确定的数据。

质量、缩放比例和最小宽度作为模块内部常量，第一版不增加配置项。上限通过
函数参数保留可测试性和未来调整空间。

## 集成

### 手动图报

`卡价图报` 在逐页发送前压缩每一页，只把压缩结果编码为 Base64。
每页只压缩一次。

### 自动日报

自动任务先为所有原始页面各生成一份 QQ 压缩副本，再把同一份副本发送给
所有管理员，避免按管理员人数重复压缩。

发送管理员完成后，B 站入口仍接收原始 PNG 页面。

### 日志

每页记录：

- 页码；
- 压缩前字节数；
- 压缩后字节数。

日志不包含图片内容或 Base64 数据。

## 错误处理

- 图片解码或压缩失败统一转为 `CardrushRenderError`。
- QQ 的 `ActionFailed(retcode=1200)` 维持现有错误处理，不自动重试。
- 某一页压缩失败时终止本次发送，避免发送一组不完整且状态不明确的图报。

## 测试

- 大型 PNG 被转换为可解码的 JPEG。
- 输出严格不超过 `1_000_000` 字节。
- 输出图片保持原始宽高比。
- 无效图片输入抛出 `CardrushRenderError`。
- 手动 QQ 图报调用压缩函数后再进行 Base64 编码。
- 自动 QQ 日报每页只压缩一次，并向多个管理员复用压缩结果。
- B 站入口仍收到原始 PNG。

## 验收标准

- 全量测试通过。
- Cardrush 范围静态检查无新增告警。
- 使用高复杂度测试图片验证每页输出不超过 1,000,000 字节。
- 真实 Playwright 图报经过 QQ 压缩后为 JPEG 且满足大小上限。
- 现有命令名称、权限、调度时间和消息文案保持不变。
